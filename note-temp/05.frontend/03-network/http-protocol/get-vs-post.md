# GET vs POST：HTTP 请求方法的本质差异

> GET 和 POST 的区别是面试高频题——但只答「GET 取数据、POST 提交数据」远远不够。从**本质**上看，差异体现在：缓存、幂等性、参数位置、安全性、浏览器行为、HTTP 语义等 9 个维度。

---

## 一、9 大核心区别速览

| 维度 | GET | POST |
|------|-----|------|
| **语义** | 只读（不应修改服务器状态） | 可能修改服务器状态 |
| **参数位置** | URL 查询字符串 | 请求体（Body） |
| **长度限制** | 受 URL 长度限制（通常 ≤ 2048 字符） | 理论上无（受服务器配置限制） |
| **缓存** | ✅ 可被浏览器 / CDN 缓存 | ❌ 默认不缓存 |
| **幂等性** | ✅ 多次调用结果一致 | ❌ 多次调用可能产生副作用 |
| **书签** | ✅ 可保存为书签 | ❌ 不可保存 |
| **浏览器历史** | ✅ 保留 | ❌ 不保留 |
| **数据类型** | 仅 ASCII（URL 编码） | 支持二进制（文件上传） |
| **SEO 友好** | ✅ URL 可被搜索引擎索引 | ❌ 数据不在 URL 中 |

---

## 二、核心用途对比

### GET —— 请求数据
- 用于**请求数据**（从服务器获取资源）
- 典型场景：搜索页面、加载文章、获取 API 数据
- 语义上表示「**只读**」操作，不应修改服务器状态
- 可以重复调用且不会产生副作用

### POST —— 提交数据
- 用于**提交数据**（向服务器发送数据并创建 / 更新资源）
- 典型场景：用户登录、表单提交、文件上传
- 语义上表示可能修改服务器状态的操作
- 重复提交需业务层防重（如幂等性 Token）

---

## 三、数据传输方式

### GET
- 数据通过 **URL 查询字符串** 传递：`?key=value&name=test`
- 数据可见于浏览器地址栏、服务器日志、HTTP 请求头
- 长度受 URL 限制（通常不超过 2048 字符）

### POST
- 数据通过 **请求体（Request Body）** 发送，不显示在 URL 中
- 支持多种格式：
  - `application/x-www-form-urlencoded`
  - `multipart/form-data`（文件上传）
  - `application/json`（RESTful API 主流）
- 理论上无长度限制（实际受服务器配置限制）

---

## 四、安全性

### GET
- **不安全**：数据暴露在 URL 中，容易被窃取或篡改
- 风险来源：浏览器历史记录、服务器日志、Referer 头、分享链接
- 适合传输非敏感数据（如搜索关键词、文章 ID）

### POST
- **相对安全**：数据不在 URL 中，但请求体仍可能被拦截
- 必须配合 **HTTPS 加密** 才能真正保障安全
- 适合传输敏感数据（密码、支付信息）

> **核心原则**：HTTPS 才是安全底线，POST 只是不把敏感数据放在 URL 上而已。

---

## 五、缓存与书签

### GET
- 请求可被浏览器缓存、保存为书签或分享（URL 包含完整信息）
- 典型场景：分享搜索结果链接、SEO 友好的内容页

### POST
- 请求通常不会被缓存或保存为书签（数据在请求体中）
- 典型场景：提交表单后无法通过书签复现操作

---

## 六、幂等性（Idempotence）

### GET —— 幂等
- 多次重复请求**不会改变服务器状态**（如多次加载同一页面）
- HTTP 规范和 RESTful 约定都要求 GET 必须幂等
- 浏览器可安全地重试 GET 请求（断网重连、刷新页面）

### POST —— 非幂等
- 多次重复提交**可能产生副作用**（重复下单、重复评论）
- 需由客户端或服务器避免重复操作：
  - 客户端：禁用提交按钮、Token 防重
  - 服务器：幂等性 Token + 业务唯一索引

---

## 七、HTTP 规范与历史

- GET 是 HTTP/0.9 最早定义的方法之一，设计初衷是简单的数据获取
- POST 在 HTTP/1.0 引入，用于需要服务器处理数据的场景（如表单提交）
- 两者均支持 HTTP/1.0 / 1.1 / 2 / 3 全版本
- 在 RESTful API 中：POST 通常用于创建资源（如 `POST /users`）

---

## 八、其他 HTTP 方法扩展

| 方法 | 幂等 | 用途 |
|------|------|------|
| **GET** | ✅ | 获取资源 |
| **POST** | ❌ | 创建资源 / 触发动作 |
| **PUT** | ✅ | 更新整个资源 |
| **PATCH** | ❌ | 部分更新资源 |
| **DELETE** | ✅ | 删除资源 |
| **HEAD** | ✅ | 类似 GET，只返回响应头（无 body） |

---

## 九、何时用 GET / POST？

### 用 GET
- 获取数据且无需修改服务器状态（搜索、分页、详情页）
- 需要缓存或分享链接的场景
- SEO 友好的内容页面

### 用 POST
- 提交数据（表单、文件上传）
- 操作可能改变服务器状态（创建订单、更新用户信息）
- 传输敏感数据（需配合 HTTPS）
- 数据量较大或包含二进制内容

---

## 十、面试话术（30s 版）

> GET 和 POST 本质上都是 HTTP 请求方法，差异体现在 9 个维度：语义上 GET 只读、POST 可能修改状态；参数位置上 GET 放 URL、POST 放 Body；GET 幂等可缓存、POST 非幂等不缓存；GET 可收藏书签、POST 不行。**真正的安全性靠 HTTPS 而不是 POST**，HTTP 规范里 GET 也不止是「取数据」——只要语义上是只读操作就可以用 GET。

---

## 十一、反直觉陷阱清单

1. **「POST 比 GET 安全」是误解**——POST 只是不把数据放 URL 上，不加密照样裸奔；安全靠 HTTPS
2. **GET 只能「取数据」是简化说法**——HTTP 规范里 GET 语义是「只读」，搜索 / 筛选 / 分页都是合法 GET
3. **GET 长度限制不是 HTTP 规范规定**——而是浏览器 / 服务器实现层限制（IE 旧版 2083 字符、Apache 默认 8190）
4. **POST 请求也能被缓存**——但需服务端主动设置 `Cache-Control` 头，浏览器默认不缓存
5. **幂等性 ≠ 安全性**——PUT 和 DELETE 也幂等，但调用错误一样会破坏数据；幂等只是「重试安全」
6. **「GET 传敏感信息」常见但危险**——密码 / Token 不应出现在 URL，否则会写入浏览器历史、服务器日志、CDN 边缘节点

---

## 十二、面试反问（候选追问）

- Q: RESTful API 一定要遵循 GET/POST/PUT/DELETE 的语义吗？
  A: 语义是约定不是强制。某些场景（如复杂查询）会用 POST + Body 传查询条件，本质是工程取舍
- Q: GET 请求能不能带 Body？
  A: HTTP/1.1 规范没禁止，但绝大多数中间设备（CDN、代理）会丢弃 GET 的 Body——生产环境**不要**依赖此行为
- Q: 浏览器刷新会重发 POST 吗？
  A: 默认会重发（浏览器会弹确认框）。为避免重复提交，服务端通常要求 POST 幂等或返回 303 重定向到结果页
