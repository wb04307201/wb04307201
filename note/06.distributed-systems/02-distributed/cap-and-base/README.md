# CAP & BASE

> ⬅️ [返回分布式](../README.md) | [共识算法](../consensus-algorithms/README.md) | [分布式事务](../distributed-transaction/README.md)

分布式系统一致性与可用性的核心理论基石——CAP 揭示了三者不可兼得的根本矛盾，BASE 给出放弃强一致性后的工程实践方案。

## 🎯 一句话定位

**CAP 告诉你"分布式三选二"，BASE 告诉你"放弃 C 后怎么落地"**——CAP 是理论边界（你不能同时拥有 CA/CP/AP 之外的系统），BASE 是工程妥协（用最终一致性换高可用）。

| 维度 | CAP | BASE |
|------|-----|------|

## 🤝 CAP 与 BASE 的关系

```text
CAP 定理告诉我们：分布式系统 P 必选（网络分区无法避免），只能在 C 和 A 之间取舍。

┌────────────┐                ┌────────────┐
│   CP 系统   │                │   AP 系统   │
│  (一致优先) │                │  (可用优先) │
│  ZooKeeper  │                │   Eureka   │
│  etcd       │                │   Cassandra│
└─────┬──────┘                └──────┬─────┘
      │                              │
      │ 放弃 A                       │ 放弃 C
      │                              │
      ▼                              ▼
   强一致方案                     弱一致方案
   (X/Open XA)                   (BASE 模型)
                                  消息队列
                                  Saga
                                  TCC
```

- **CAP 是理论**：告诉你"做不到"
- **BASE 是方案**：教你"怎么做到"
- **现代分布式系统**：大多选择 **AP + BASE**（用最终一致性换可用性）

## 速记卡：split-hairs 视角

> 本节为 split-hairs 迁出内容（2026-08-10），保留面试深挖价值，避免与上方概念铺陈重复。

### 30 秒面试话术（CP/AP 选型版）

> "CAP 定理说分布式系统中一致性、可用性、分区容错性三者最多满足两个。由于网络分区不可避免，P 是底线，所以实际是在 CP 和 AP 之间做选择。
>
> ZooKeeper、etcd 这类系统走 CP 路线，通过 Raft/ZAB 等共识协议保证强一致，代价是分区时少数派不可用；而 Eureka、Cassandra 走 AP 路线，保证任何时候都能读写，但数据可能暂时不一致。
>
> 实际选型要看业务：服务注册中心选 AP，因为短暂读到过期服务列表影响不大，但注册功能不能挂；分布式锁和配置中心必须选 CP，因为锁失效或配置不一致会导致严重问题。BASE 理论就是对 AP 方案的工程化指导，通过最终一致性来平衡体验和复杂度。"

### 3 大反直觉陷阱

| 陷阱 | 直觉以为 | 实际真相 |
|------|---------|---------|
| **"三选二 = 自由组合"** | 想放弃哪个都行 | **P 是底线必选**——网络分区不可避免，实际只剩 CP/AP 二选一 |
| **"CP = 强一致 = 好"** | CP 系统更"高级" | 强一致是有代价的——分区时少数派**直接拒绝服务**，可用性归零 |
| **"AP = 不一致 = 差"** | AP 系统"差" | AP 不等于"随便写"——通过 **BASE 5 大一致性级别**（因果/读己之写/会话/单调读/单调写）控制不一致范围 |

### 选型决策矩阵（实战速查）

| 业务场景 | 推荐类型 | 核心理由 |
|----------|----------|---------|
| **服务注册中心** | AP | 短暂读到过期服务列表影响不大，但注册功能不能挂 |
| **分布式锁** | CP | 锁的正确性依赖强一致，否则出现双写 |
| **配置中心** | CP | 配置错误可能导致大面积故障，需强一致 |
| **分布式 ID 生成** | CP | ID 不能重复，需全局有序 |
| **社交 Feed 流** | AP | 用户能接受动态延迟加载 |

### 混合架构心法

现代系统**几乎从不单一选 CP 或 AP**，而是分层组合：

```text
┌─────────────────────────────────────────┐
│           API Gateway (AP)              │  ← 高可用接入层
├─────────────────────────────────────────┤
│     业务服务层（无状态，水平扩展）        │  ← 通过幂等性+重试补偿
├─────────────────────────────────────────┤
│   缓存层 Redis (AP)  │  DB MySQL (CP)   │  ← 读写分离，最终一致
├─────────────────────────────────────────┤
│    协调层 ZooKeeper/etcd (CP)           │  ← 分布式锁/选主
└─────────────────────────────────────────┘
```

**3 条核心设计原则**：

1. **核心链路 CP，非核心链路 AP**：支付、扣库存走强一致；浏览历史、推荐走最终一致
2. **写路径 CP，读路径 AP**：写入走共识协议保证正确，读取走副本提升吞吐
3. **本地事务 + 消息队列实现最终一致**：通过事务消息、Saga、TCC 等模式补偿

### 面试反问模板

```text
Q1：你们 CAP/AP 怎么选？依据是什么？
    → 答：业务对一致性 vs 可用性的容忍度
Q2：分区发生时你们怎么处理？
    → 答：CP 牺牲少数派、AP 接受短期不一致靠补偿收敛
Q3：为什么 ZooKeeper 不直接做 AP？
    → 答：它的核心场景（锁/选主/配置）强依赖一致性，AP 会导致脑裂
```

## 🤔 思考

1. **CAP 真的只能三选二吗？** 严格说是"分区发生时三选二"；无分区时 C+A 都可满足。
2. **BASE 就是不用事务吗？** 不是，是"事务弱化"——把全局事务拆为本地事务 + 补偿。
3. **Eureka 为什么是 AP？** 服务发现场景下宁可暂时不一致（拿到旧地址），也要保证可用性。
4. **什么时候该选 CP？** 强一致场景：金融、库存扣减、分布式锁。
