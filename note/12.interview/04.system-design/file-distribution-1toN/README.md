# 设计 1 万人接收 200M 大文件 —— 1→N 大文件分发

> 一句话定位：**后端 / 架构面试经典系统设计题**。考察的不是"文件怎么传"，而是 **带宽成本估算 + CDN / P2P / 边缘分发选型 + 高并发下载 + 断点续传 + 安全合规**。深度实战见主模块 [高性能篇之 file-upload](../../../06.distributed-systems/04-high-performance/file-upload/README.md)（用户上传视角，已沉淀 191 行）。

> **系列定位**：高频系统设计题（社招必考 / 抖音/B 站面试原题）。配套兄弟题：[大文件上传系统](../file-upload/README.md)（用户上传视角互补）、[消息已读未读](../message-read-status/README.md)、[媒体上传](../media-upload/README.md)。

## 引子：面试经典开场

面试官："设计一个系统：服务端要把一个 200M 文件发给 1 万个用户，每个用户都需在 5 分钟内下载完成，怎么设计？"

大多数人答："用 CDN 加速。"

面试官追问：

1. **带宽成本**是多少？1 万 × 200M = 2TB 出流量，光 CDN 费用就几千块一次？
2. CDN 失效 / 冷门文件怎么办？（**P2P / 边缘缓存**？）
3. 下载过程中网络断了，怎么断点续传？
4. 怎么防**恶意刷量**（一个用户下载 100 次冒充 100 个用户）？
5. 文件内容敏感（合同 / 财报）怎么**防盗链 + 限速**？

大多数人卡在追问上。**这道题考察的不是"用 CDN"，而是"带宽成本 + CDN/P2P 选型 + 高并发 + 断点续传 + 安全"**。

---

## 一、核心问题拆解

### 1.1 1 万 × 200M 的成本估算

- **总数据量**：10,000 × 200M = **2 TB**
- **完成时间**：5 分钟 = 300 秒
- **所需带宽**：2 TB / 300 s = **6.8 GB/s** ≈ **54 Gbps**
- **CDN 成本**（以 0.18 元/GB 计）：2 TB × 1000 GB/TB × 0.18 = **360 元 / 次**
- **带宽成本**（自建，按 100 Mbps 单线带宽 5000 元/月）：54 Gbps 远超单线 → **需 CDN**

### 1.2 5 大核心挑战

1. **带宽成本**：2 TB 数据分发，单次几百元 CDN 费
2. **下载并发**：1 万同时下载（瞬时连接数）
3. **断点续传**：用户网络中断后恢复下载
4. **防盗链**：防止文件被未授权下载
5. **下载限速**：避免单用户占满带宽

### 1.3 三大非功能性需求

- **下载速度**：单用户 ≥ 10 Mbps（200M / 200s ≈ 3 分钟）
- **可靠性**：下载成功率 > 99.9%
- **安全**：防盗链 + 鉴权 + 防泄漏

## 二、4 大主流方案演进

### 2.1 方案 1：单源服务器直传（撑不住，参考用）

**架构**：

```text
1 万客户端 → 单源服务器（200M 文件）→ 直接 HTTP 下载
```

**瓶颈**：

- 单机带宽：1 Gbps ≈ 125 MB/s
- 1 万用户同时下载 → 1.6 GB/s（远超标）
- 服务器必崩

**结论**：❌ 完全不可行

### 2.2 方案 2：CDN 边缘加速（推荐，标准方案）

**架构**：

```text
源站（OSS）→ CDN 边缘节点（全国/全球 100+ 节点）
                ↓
        1 万客户端就近下载
```

**关键设计**：

- **源站**：OSS / S3 存文件（冷源）
- **CDN**：阿里云 / AWS CloudFront / Cloudflare（边缘缓存）
- **回源策略**：首次访问回源 → CDN 缓存 → 后续直接命中
- **预热（Cache Prefetch）**：大促前主动推送热点文件到边缘

**优点**：

- 解决带宽瓶颈（边缘节点分散带宽压力）
- 全球加速（用户就近下载）
- 简单可靠（CDN 服务成熟）

**缺点**：

- 成本：2 TB 流量费用（360+ 元 / 次，量大可观）
- 冷门文件 CDN 命中率低
- 单一 CDN 服务商风险

### 2.3 方案 3：CDN + P2P 混合（成本优化，百万级）

**架构**：

```text
源站 → CDN 边缘 → 客户端 A 下载（首次）
                → 客户端 B 下载 → 发现 CDN 已有 A 缓存
                → 同时 A 和 B 之间建立 P2P 连接
                → B 从 A 拉取部分分片
```

**关键技术**：

- **P2P 客户端 SDK**：用户首次下载走 CDN，后续用户从已下载用户拉取
- **BitTorrent 协议**：分片 + 多源下载
- **Tracker 服务器**：协调哪些用户有需要的分片
- **WebRTC / QUIC**：浏览器内 P2P 传输

**优点**：

- **成本降低 50-70%**：CDN 流量被 P2P 分流
- 适合大文件 / 大规模分发（抖音/B 站视频分发）
- 边缘节点压力小

**缺点**：

- 实现复杂（需自研 / 接入第三方 SDK）
- 用户体验略差（部分分片来自其他用户）
- 隐私 / 合规风险（用户间互传敏感文件）

### 2.4 方案 4：分片签名 + 短期 URL（安全 + 防泄漏）

**架构**：

```text
源站生成短期签名 URL（5 分钟过期）
  ↓
1 万客户端用签名 URL 下载（每个用户唯一 URL）
  ↓
URL 过期后无法继续下载
```

**关键设计**：

- **签名 URL**：HMAC(secret, path + expire_time)
- **下载限速**：CDN 配置单 IP 限速 50 Mbps
- **下载次数限制**：每个 URL 只能下载 N 次
- **Referer 白名单**：只允许指定页面下载
- **Token 鉴权**：URL 中携带用户 ID + 临时 token

**适用**：合同 / 财报 / 软件分发等敏感场景

## 三、4 大方案对比矩阵

| 维度 | 单源直传 | CDN 边缘 | CDN + P2P | 分片签名 + 短期 URL |
|------|---------|---------|-----------|---------------------|
| 适用规模 | <10 | 100-100 万 | **10 万+** | 任意（敏感场景） |
| 单次成本 | 服务器必崩 | **360+ 元** | **100-180 元** | 360+ 元 + 鉴权 |
| 下载速度 | 慢 | 快 | 中快 | 快 |
| 实现复杂度 | 极低 | 低 | 高 | 中 |
| 防盗链 | 无 | ⚠️ 中 | ⚠️ 中 | ✅ 强 |
| 推荐场景 | Demo | **通用方案** | 大平台视频分发 | 敏感文件分发 |

## 四、断点续传设计

### 4.1 HTTP Range 协议（核心机制）

```http
GET /file.zip HTTP/1.1
Range: bytes=1048576-2097151  # 请求 1-2 MB 分片
```

**服务器响应**：

```http
HTTP/1.1 206 Partial Content
Content-Range: bytes 1048576-2097151/209715200
Content-Length: 1048576
```

### 4.2 客户端断点续传实现

- **首次下载**：记录已下载字节数（localStorage）
- **网络中断**：下次启动从 localStorage 读取 Range
- **服务器校验**：校验 Etag / Last-Modified 是否变化（文件未更新才续传）

### 4.3 服务端 Range 支持

- **OSS / CDN**：天然支持 Range（无需自实现）
- **自建文件服务**：需在响应头加 `Accept-Ranges: bytes`
- **不支持 Range 的服务器**：客户端只能用整文件下载

## 五、防盗链 + 安全

### 5.1 5 大防盗链策略

| 策略 | 原理 | 适用 |
|------|------|------|
| **Referer 白名单** | 检查 HTTP Referer | 公开资源 |
| **签名 URL** | HMAC 签名 + 过期时间 | **敏感文件首选** |
| **Token 鉴权** | URL 携带一次性 token | 高安全 |
| **IP 限速** | CDN 单 IP 限速 50 Mbps | 防爬虫 |
| **下载次数限制** | URL 只能下载 N 次 | 防止扩散 |

### 5.2 敏感文件分发 checklist

- ✅ 签名 URL（5 分钟过期）
- ✅ Token 一次性（使用即失效）
- ✅ 单 IP 限速（避免单用户刷量）
- ✅ Referer 白名单（防止直链）
- ✅ 水印（PDF / 图片加用户 ID 水印）
- ✅ 下载日志审计（合规追溯）

---

## 六、高并发下载优化

### 6.1 CDN 边缘缓存策略

- **首次访问**：CDN 回源 → 缓存 → 返回
- **后续访问**：CDN 直接返回（命中率 95%+）
- **大文件预热**：分发前主动推送到所有边缘节点
- **回源限速**：源站保护，避免被 CDN 拉爆

### 6.2 并发连接优化

- **HTTP/2 / HTTP/3**：单连接多路复用
- **分片并发下载**：前端 file-slicing 拆 10 个分片并行
- **QUIC 协议**：减少 TCP 握手延迟

### 6.3 下载进度监控

- 客户端进度上报（每 5 秒一次）
- 服务端聚合：当前下载人数 / 平均速度 / 完成率
- 失败告警：成功率 < 95% 时报警

---

## 七、5 大反模式

### ❌ 反模式 1：单源服务器直传

- 错：1 万用户都从单台服务器下载
- 对：CDN 边缘 + 多节点分发

### ❌ 反模式 2：忽略带宽成本

- 错：上线后才发现 CDN 费用爆炸
- 对：预估成本 + 预算审批 + P2P 降本

### ❌ 反模式 3：没有断点续传

- 错：网络中断要从头下载
- 对：HTTP Range + 客户端 localStorage 续传

### ❌ 反模式 4：URL 长期有效

- 错：URL 永不过期，文件被无限传播
- 对：签名 URL + 短期过期（5 分钟）+ 一次性

### ❌ 反模式 5：没有下载日志审计

- 错：谁下载了什么不清楚
- 对：完整下载日志（用户 ID / 时间 / IP）→ 合规审计

## 八、面试高频追问

### Q1：1 万 × 200M 的带宽成本怎么算？

答：2 TB 数据 / 300 秒 ≈ 6.8 GB/s ≈ 54 Gbps。CDN 按 0.18 元/GB 计 ≈ 360 元/次。自建需 54 Gbps 专线（月费数万），故优选 CDN。

### Q2：CDN 和 P2P 怎么选？什么场景用 P2P？

答：通用分发用 CDN（简单可靠）；百万级 / TB 级 / 视频直播等高成本场景用 P2P 混合（B 站、抖音）。P2P 降本 50-70%，但实现复杂、隐私合规风险高。

### Q3：断点续传怎么实现？HTTP Range 协议是什么？

答：客户端记录已下载字节（localStorage），下次请求携带 `Range: bytes=start-end` 头。服务器响应 `206 Partial Content` 返回分片。OSS / CDN 天然支持，自建文件服务需在响应头加 `Accept-Ranges: bytes`。

### Q4：怎么防恶意刷量？防盗链有哪些策略？

答：5 大策略叠加：签名 URL + 短期过期 + Token 一次性 + 单 IP 限速 + Referer 白名单。配合下载日志审计（用户 ID / 时间 / IP），发现异常 IP 拉黑。

### Q5：敏感文件（合同 / 财报）怎么分发才安全？

答：4 层防线——① 签名 URL（5 分钟过期、一次性）；② 单 IP 限速（避免刷量）；③ PDF / 图片加水印（用户 ID）；④ 下载日志审计 + 异常告警。

### Q6：CDN 命中率低怎么办？冷门文件怎么分发？

答：3 种方案——① 大文件预热（分发前推送到所有边缘节点）；② 多 CDN 厂商容灾（避免单点）；③ 冷门文件走对象存储直连 + 长尾备份到 OSS 归档存储。

### Q7：HTTP/2 / HTTP/3 / QUIC 对大文件分发有什么优化？

答：HTTP/2 单连接多路复用（避免 6 个 TCP 连接握手）；HTTP/3 基于 UDP/QUIC（解决 TCP 队头阻塞，移动网络切换不掉线）；分片并发下载提升吞吐 30%+。

### Q8：用户下载完成后怎么清理 CDN 缓存？

答：分场景——① 长期热点文件：保留缓存；② 临时分发（如活动素材）：配置 CDN TTL（24h 自动失效）；③ 敏感文件：分发完成后调用 CDN 的 purge API 主动清除。
