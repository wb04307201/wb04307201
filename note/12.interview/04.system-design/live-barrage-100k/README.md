# 设计 10 万人直播间的弹幕系统 —— 高并发实时消息分发

> 一句话定位：**后端 / 架构面试经典系统设计题**。考察的不是"消息怎么发"，而是 **WebSocket 长连接管理 + 10 万级并发推送 + 消息分层分发 + 限流/敏感词过滤 + 抗雪崩**。深度实战见主模块高性能篇 / 消息队列篇。

> **系列定位**：高频系统设计题（社招必考 / B 站/抖音面试原题）。配套兄弟题：[缓存一致性](../cache-consistency/README.md)、[限流算法](../rate-limiting/README.md)、[消息已读未读](../message-read-status/README.md)、[无 Redis 秒杀](../seckill-without-redis/README.md)。

⭐⭐⭐⭐⭐ 深度级别（架构师级）
📚 前置知识：WebSocket / 消息队列 / Redis / 长连接 / 限流

---

## 引子：面试经典开场

面试官："设计一个 10 万人同时观看的直播弹幕系统，每秒峰值 5 万条弹幕，要求端到端延迟 < 1s。"

大多数人答："用 WebSocket 长连接 + 消息队列广播。"

面试官追问：

1. 10 万 WebSocket 连接怎么管理？单机瓶颈在哪？
2. 弹幕怎么避免"被恶意刷屏"？（限流 + 敏感词）
3. "热门直播间"的弹幕洪峰怎么抗？（流量削峰 + 分层过滤）
4. 用户进直播间时，错过历史弹幕要不要补发？怎么补？

大多数人卡在追问上。**这道题考察的不是"知道 WebSocket"，而是"长连接架构 + 高并发推送 + 消息分层 + 抗洪峰 + 体验一致性"**。

---

## 一、核心问题拆解

### 1.1 10 万人直播间的压力有多大？

- 假设：10 万在线，每人 5 秒发 1 条弹幕
- **峰值 QPS**：100,000 / 5 = **20,000 条/秒**
- 假设每条弹幕 50 字节，**峰值带宽**：20,000 × 50B = **1MB/s**（不算大）
- **核心瓶颈**：20,000 条/秒 × 10 万订阅 = **20 亿次推送/秒**（每条弹幕要推给所有观众）

### 1.2 三大核心挑战

1. **海量连接管理**：10 万 WebSocket 长连接
2. **消息广播风暴**：1 条弹幕 → 10 万次推送
3. **实时性保证**：端到端延迟 < 1s

### 1.3 5 大非功能性需求

- **实时性**：端到端 < 1s
- **可靠性**：不丢消息（用户发的弹幕不能消失）
- **一致性**：所有人看到顺序一致
- **安全性**：敏感词过滤 + 限流
- **可扩展性**：支持 100 万观众的超大直播间

---

## 二、4 大主流方案演进

### 2.1 方案 1：单机 WebSocket + 广播（最简单，撑不住 10 万）

**架构**：

```text
客户端 → 单机 WebSocket Server（Node.js/Java）→ 广播给所有连接
```

**瓶颈**：

- 单机连接数：~5-10 万（C10K 问题）
- 单机推送能力：~1 万/秒
- 10 万人 + 20,000 条/秒：**单机 100% 撑不住**

**适用**：仅 Demo / 几千人小直播间

### 2.2 方案 2：WebSocket 网关集群 + Redis Pub/Sub（中等规模）

**架构**：

```text
用户 → WebSocket 网关集群（N 台，每台 5 万连接）
     → 弹幕消息发到 Redis Pub/Sub 频道（直播间 ID 为频道名）
     → 所有网关订阅频道 → 推送给本机连接的用户
```

**关键设计**：

- **网关集群**：N 台机器分担连接（每台 5 万连接）
- **Redis Pub/Sub**：跨机器消息分发（10 万连接都能收到）
- **同房间聚合**：同一直播间的连接尽量落在同一网关（减少跨机推送）

**优点**：

- 解决单机瓶颈
- 实现相对简单
- 适合 10 万级观众

**缺点**：

- Redis Pub/Sub 不持久化（重启会丢消息）
- 跨机房部署复杂
- 热门直播间单房间消息量仍可能压垮 Redis

### 2.3 方案 3：消息队列分层 + 多级推送（推荐，百万级）

**架构**：

```text
用户 → WebSocket 网关集群
发送弹幕 → API 网关 → Kafka（弹幕 topic，按直播间分区）
        → 多组消费者并行处理
        → 按房间分组（同一房间消息合并）
        → WebSocket 网关订阅本房间 → 推送给连接用户
```

**关键设计**：

- **Kafka 分区**：按直播间 ID 分区（同一直播间消息顺序一致）
- **消息合并**：500ms 窗口内的弹幕合并推送（前端展示平滑）
- **多级推送**：边缘推送 + 长轮询兜底
- **降级策略**：WebSocket 故障自动降级为 SSE / 长轮询

**优点**：

- 持久化（Kafka 不丢消息）
- 横向扩展（消费者可动态扩缩容）
- 顺序保证（同直播间消息有序）

**缺点**：

- 架构复杂
- 引入 Kafka 依赖

### 2.4 方案 4：直播流内嵌（最低延迟，最复杂）

**架构**：

```text
弹幕随直播流一起推到 CDN 边缘节点
CDN 在推流给客户端时把弹幕一并打包
```

**优点**：

- 极低延迟（与视频同步）
- CDN 全球分发

**缺点**：

- 实现复杂（需自定义 CDN 协议）
- 弹幕与视频强耦合

| 维度 | 单机 WebSocket | 集群 + Redis Pub/Sub | MQ 分层 | 流内嵌 |
|------|---------------|---------------------|---------|--------|
| 适用规模 | <1 万 | 1-10 万 | 10-100 万 | 100 万+ |
| 端到端延迟 | <100ms | <500ms | <1s | <200ms |
| 实现复杂度 | 极低 | 低 | 中 | 高 |
| 持久化 | ❌ | ❌ | ✅ | ✅ |
| 顺序保证 | ✅ | ⚠️ 跨机 | ✅ | ✅ |
| 推荐场景 | Demo | 中等直播 | **B 站/抖音** | 体育直播 |

## 四、弹幕的核心机制详解

### 4.1 发送弹幕流程

```text
1. 客户端发送弹幕 → WebSocket 网关
2. 网关校验：限流（每秒最多 X 条）+ 敏感词过滤 + 内容长度
3. 写入 Kafka（topic=live_barrage，分区=room_id）
4. Kafka 消费者订阅 → 合并 / 排序 / 二次过滤
5. 推送到 WebSocket 网关（订阅本房间的所有网关节点）
6. 网关推送给本机所有该房间的连接用户
```

### 4.2 接收弹幕流程

```text
1. 客户端建立 WebSocket 连接（携带 token + room_id）
2. 网关鉴权 + 绑定 room_id 到连接
3. 网关订阅 Kafka room_id 分区（或通过 Redis 转发）
4. 收到消息后 → 直接推送给本机用户
```

### 4.3 用户进直播间的"补发历史弹幕"

- 拉取最近 N 条（如最近 30 条）作为上下文
- 存储：Redis List（room_id → 最近 N 条弹幕）
- 过期：超过 N 条自动 LRU 淘汰

## 五、高并发推送优化（百万观众）

### 5.1 消息合并（关键优化）

- 单条弹幕太碎（20,000 条/秒对前端是洪水）
- **窗口合并**：500ms 窗口内的弹幕合并推送（前端 JS 拆开显示）
- **效果**：客户端推送频率降到 2,000 次/秒（10 倍优化）

### 5.2 同房间聚合推送

- 把同一房间的连接尽量落到同一台网关（一致性哈希）
- 减少跨机推送（每条弹幕只在本机推送 1 次）

### 5.3 弹幕采样（百万观众）

- 不是所有观众都看弹幕（很多人只看视频）
- **服务端采样**：只推给"开了弹幕显示"的用户
- **客户端节流**：浏览器 setTimeout 控制渲染频率（<10 条/秒）

### 5.4 优先级队列

- VIP 弹幕 / 礼物弹幕（高优先级）
- 普通弹幕（普通优先级）
- 高优先级优先推送

## 六、5 大反模式

### ❌ 反模式 1：单机扛 10 万连接

- 错：单台服务器撑 10 万 WebSocket
- 对：网关集群 + 一致性哈希分布

### ❌ 反模式 2：每条弹幕推 10 万次

- 错：1 条弹幕 → 10 万次推送（O(N²) 复杂度）
- 对：消息合并 + 同房间聚合（O(N) 复杂度）

### ❌ 反模式 3：没有限流导致恶意刷屏

- 错：用户可无限发弹幕
- 对：每用户限流（令牌桶 1 条/秒）+ 全局限流

### ❌ 反模式 4：敏感词过滤在前端

- 错：客户端过滤（可绕过）
- 对：服务端敏感词过滤 + Aho-Corasick 算法

### ❌ 反模式 5：弹幕持久化用同步 DB 写

- 错：弹幕同步写 MySQL（延迟爆炸）
- 对：异步写 Kafka + 离线落库（ClickHouse / HBase）

## 七、面试高频追问

### Q1：10 万 WebSocket 连接怎么管理？

**要点**：

- 网关集群（N 台机器分担连接）+ 一致性哈希（连接落到固定机器）
- 心跳保活（30s ping/pong）+ 断线重连（指数退避）
- 连接状态管理：本地 Map + Redis 共享（跨机器查询）

### Q2：弹幕怎么限流？怎么防刷屏？

**要点**：

- **用户级限流**：令牌桶（1 条/秒，桶容量 5）
- **房间级限流**：滑动窗口（房间总 QPS 上限 50,000）
- **敏感词过滤**：Aho-Corasick 多模式匹配（O(n) 复杂度）
- **行为分析**：同 IP 同账号短时间内大量发送 → 验证码 / 封禁

### Q3：Redis Pub/Sub vs Kafka 怎么选？

**要点**：

| 维度 | Redis Pub/Sub | Kafka |
|------|---------------|-------|
| 持久化 | ❌ 消息不落地 | ✅ 持久化到磁盘 |
| 顺序保证 | ⚠️ 跨机乱序 | ✅ 分区内有序 |
| 吞吐 | ~10 万/秒 | ~百万/秒 |
| 适用 | 中等直播（<10 万） | 大型直播（百万级） |

**选型建议**：10 万以下用 Redis Pub/Sub（简单）；百万级用 Kafka（持久化 + 顺序）。

### Q4：热门直播间（百万观众）弹幕怎么优化？

**要点**：

- **消息合并**：500ms 窗口合并（10 倍推送频率优化）
- **服务端采样**：只推给"开启弹幕显示"的用户（<50%）
- **CDN 边缘分发**：弹幕服务部署到 CDN 边缘节点（就近推送）
- **降级策略**：超阈值时只推 VIP / 礼物弹幕（普通弹幕降级为轮询）

### Q5：用户进直播间错过的弹幕要不要补？怎么补？

**要点**：

- **不补全量**（性能差 + 用户不需要）
- **补最近 N 条**（如最近 30 条，作为上下文）
- 存储：Redis List（room_id → 最近 N 条弹幕，超过自动 LRU 淘汰）
- 进入直播间时一次性下发，前端渲染在视频上方

### Q6：弹幕顺序怎么保证全局一致？

**要点**：

- Kafka 按 room_id 分区（同房间消息有序）
- 消费者按时间戳排序（timestamp 字段）
- 服务端生成单调递增 seq，前端按 seq 渲染（避免乱序）
- 跨房间不需要全局有序（按房间独立）

### Q7：弹幕怎么持久化存储？

**要点**：

- **不要同步写 DB**（延迟爆炸）
- **异步写 Kafka** + 离线消费落库
- **存储选型**：
  - 实时查询最近 N 条 → Redis List
  - 全量历史弹幕 → ClickHouse（列存，OLAP 友好）
  - 用户维度查询 → HBase（宽表，亿级）
- **冷热分离**：3 天内热数据 Redis，3 天外冷数据 ClickHouse

## 八、生产级实践要点（补充）

### 8.1 WebSocket 心跳与断线重连

- **心跳间隔**：30s（平衡"发现断线"与"流量开销"）
- **心跳超时**：3 次未响应 → 主动断开
- **重连策略**：指数退避（1s → 2s → 4s → 8s，最大 30s）
- **断线补发**：连接恢复时拉取断线期间未收到的消息（按 seq）

### 8.2 推流协议对比

- **WebSocket**：双向通信，主流（弹幕 + 信令）
- **SSE**：服务端单向推送，断线自动重连（适合纯接收弹幕）
- **HTTP 长轮询**：兼容性最好（兜底方案）
- **QUIC / HTTP3**：未来趋势（弱网优化）

### 8.3 监控指标

- **连接数**：每台网关的活跃 WebSocket 连接数
- **消息吞吐**：发送 / 接收 QPS
- **端到端延迟**：从发送到所有用户收到的 P99 延迟
- **丢消息率**：按 seq 检测（应当为 0）
- **错误率**：连接断开 / 鉴权失败比例
